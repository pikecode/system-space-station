# 客户投资收益管理设计

> 日期：2026-08-18  
> 状态：已确认，第一阶段实施中  
> 适用范围：产品管理、客户投资、产品周期收益、客户收益展示、内部分配与结算

---

## 一、背景与目标

客户正式入会后会进行投资，投资会购买一个产品。产品在后续周期中产生收益，后台需要维护收益信息，并按一定周期同步到客户投资收益中。客户登录小程序后，应能查看自己的投资产品、投资金额、周期收益、累计收益和结算状态。

同时，公司内部还需要根据后台配置的收益分配比例，把收益拆分给客户、部门、签约员工、录入员工和公司。该分配明细用于内部管理和结算，客户小程序只展示客户自己的收益，不展示内部人员和部门分配。

核心目标：

1. 支持后台维护产品。
2. 支持正式会员客户购买产品并形成投资记录。
3. 支持按周期维护产品收益。
4. 支持把产品收益同步到客户投资收益。
5. 支持按后台配置比例生成收益分配明细。
6. 支持客户小程序查看自己的投资和收益。

已确认边界：

1. 产品收益按“产品总收益”录入。
2. 第一阶段不做持有天数加权。
3. 第一阶段不做中途追加和部分退出。
4. 收益分配比例采用全局统一配置。
5. 客户小程序只展示客户分配后的实际到账收益，后台保留完整计算链路。
6. 收益结算第一阶段采用后台手动结算。

---

## 二、核心结论

推荐采用 **方案 A：产品 + 投资 + 收益周期 + 收益分配明细**。

```text
InvestmentProduct 产品
  ↓
CustomerInvestment 客户投资
  ↓
ProductYieldPeriod 产品周期收益
  ↓
CustomerProfitRecord 客户收益记录
  ↓
ProfitShareRecord 收益分配明细
```

这个结构把“产品收益”和“客户收益”拆开，既能记录产品层面的收益，也能记录每个客户按投资份额获得的收益，还能保留内部收益分配明细。

## 三、方案对比

### 方案 A：产品、投资、收益、分配分表设计（推荐）

新增产品、客户投资、产品周期收益、客户收益、收益分配配置、收益分配明细等表。

优点：

- 结构清晰，业务含义明确。
- 支持一个客户购买多个产品。
- 支持一个产品多个收益周期。
- 支持客户收益和内部分配分别展示。
- 历史收益和比例快照可追溯。

缺点：

- 需要新增多张表和后台页面。
- 第一阶段实现成本高于简单字段方案。

### 方案 B：直接在客户或会员表增加收益字段

在客户表或会员表增加投资金额、累计收益、本期收益等字段。

优点：

- 改动少，上线快。

缺点：

- 无法支持多个产品。
- 无法追踪每期收益。
- 无法还原历史分配比例。
- 后续做结算和报表会变复杂。

### 方案 C：复用现有 `CommissionRecord`

把投资收益也写入现有会员费分成表。

优点：

- 可以复用部分结算状态和列表逻辑。

缺点：

- 会员费分成和投资收益分配语义不同。
- 客户收益、产品收益和员工佣金混在一起，后续报表容易混乱。
- 不利于客户小程序展示。

结论：推荐方案 A。

## 四、核心业务概念

### 4.1 产品

产品是客户投资购买的对象，例如固定收益产品、项目投资产品、基金类产品等。

产品需要记录：

- 产品名称。
- 产品编码。
- 产品类型。
- 风险等级。
- 起投金额。
- 产品状态。
- 预计开始和结束日期。
- 备注。

### 4.2 客户投资

客户投资表示某个正式会员购买某个产品。

客户投资需要记录：

- 客户。
- 产品。
- 投资金额。
- 投资日期。
- 投资状态。
- 签约人快照。
- 签约部门快照。
- 录入人快照。

客户投资只能由正式会员产生。意向会员、待审批、待缴费客户不能创建投资记录。

### 4.3 产品周期收益

产品周期收益表示某个产品在某个周期内产生的总收益。

例如：

```text
产品：稳健增长一号
周期：2026-09-01 至 2026-09-30
总收益：100000
```

后台确认该周期收益后，系统根据该产品下客户投资金额占比生成客户收益记录。

### 4.4 客户收益

客户收益表示某个客户某笔投资在某个收益周期获得的收益。

例如：

```text
客户投资：客户 A 投资 100 万
产品总投资：1000 万
产品本期收益：10 万
客户占比：10%
客户本期收益：1 万
```

客户收益是客户小程序展示的核心数据。

### 4.5 收益分配明细

收益分配明细表示客户收益在内部和客户之间如何拆分。

例如客户收益为 10000 元，后台配置：

```text
客户 60%
部门 15%
签约员工 10%
录入员工 10%
公司 5%
```

生成：

```text
客户收益：6000
部门收益：1500
签约员工收益：1000
录入员工收益：1000
公司收益：500
```

客户小程序只展示客户收益部分。后台可查看完整分配明细。

第一阶段实现说明：

- 后台提供产品、客户投资、产品收益、客户收益和收益分配比例维护入口。
- 产品收益确认后，系统按产品下有效投资金额占比生成客户收益记录。
- 客户收益记录同时生成客户、部门、签约人、录入人、公司五类分配明细。
- 客户小程序展示投资产品和客户实际到账收益，不展示内部收益分配。

## 五、数据模型设计

### 5.1 产品表：`InvestmentProduct`

```prisma
enum InvestmentProductStatus {
  DRAFT
  ACTIVE
  CLOSED
  ARCHIVED
}

model InvestmentProduct {
  id              String                  @id @default(cuid())
  productNo       String                  @unique
  name            String
  productType     String?
  riskLevel       RiskTolerance?
  minAmount       Decimal?                @db.Decimal(12, 2)
  expectedStartAt DateTime?
  expectedEndAt   DateTime?
  status          InvestmentProductStatus @default(DRAFT)
  remark          String?
  createdBy       String
  createdAt       DateTime                @default(now())
  updatedAt       DateTime                @updatedAt
}
```

### 5.2 客户投资表：`CustomerInvestment`

```prisma
enum CustomerInvestmentStatus {
  ACTIVE
  EXITED
  CANCELLED
}

model CustomerInvestment {
  id                     String                   @id @default(cuid())
  investmentNo           String                   @unique
  customerId             String
  productId              String
  amount                 Decimal                  @db.Decimal(12, 2)
  investedAt             DateTime
  status                 CustomerInvestmentStatus @default(ACTIVE)

  contractedBy           String?
  contractedEmployeeNo   String?
  contractedDepartmentId String?
  createdBy              String
  createdEmployeeNo      String?
  createdDepartmentId    String?

  createdAt              DateTime                 @default(now())
  updatedAt              DateTime                 @updatedAt
}
```

说明：

- `customerId` 必须指向正式会员客户。
- `amount` 是该客户在产品中的投资本金。
- 签约人、录入人、部门都保存快照，防止人员离职或调岗后历史收益无法追溯。

### 5.3 产品周期收益表：`ProductYieldPeriod`

```prisma
enum ProductYieldStatus {
  DRAFT
  CONFIRMED
  CANCELLED
}

model ProductYieldPeriod {
  id            String             @id @default(cuid())
  productId     String
  periodStart   DateTime
  periodEnd     DateTime
  totalProfit   Decimal            @db.Decimal(12, 2)
  status        ProductYieldStatus @default(DRAFT)
  confirmedBy   String?
  confirmedAt   DateTime?
  remark        String?
  createdBy     String
  createdAt     DateTime           @default(now())
  updatedAt     DateTime           @updatedAt

  @@unique([productId, periodStart, periodEnd])
}
```

说明：

- 同一产品同一周期只能有一条收益记录。
- `CONFIRMED` 后才能生成客户收益。
- 如收益填错，建议用取消或冲正方式处理，不直接覆盖历史。

### 5.4 客户收益记录表：`CustomerProfitRecord`

```prisma
enum CustomerProfitStatus {
  PENDING
  CONFIRMED
  SETTLED
  CANCELLED
}

model CustomerProfitRecord {
  id              String               @id @default(cuid())
  customerId      String
  investmentId    String
  productId       String
  yieldPeriodId   String
  principalAmount Decimal              @db.Decimal(12, 2)
  profitAmount    Decimal              @db.Decimal(12, 2)
  ratioSnapshot   Decimal              @db.Decimal(12, 6)
  status          CustomerProfitStatus @default(PENDING)
  createdAt       DateTime             @default(now())
  settledAt       DateTime?

  @@unique([investmentId, yieldPeriodId])
}
```

说明：

- `principalAmount` 保存计算时的本金快照。
- `ratioSnapshot` 保存客户投资占产品总投资的比例。
- `profitAmount` 是客户该周期可参与分配的收益金额。

### 5.5 收益分配配置表：`ProfitShareConfig`

```prisma
model ProfitShareConfig {
  id                  String   @id @default(cuid())
  customerRatio        Decimal  @db.Decimal(5, 2)
  departmentRatio      Decimal  @db.Decimal(5, 2)
  contractedUserRatio  Decimal  @db.Decimal(5, 2)
  createdUserRatio     Decimal  @db.Decimal(5, 2)
  companyRatio         Decimal  @db.Decimal(5, 2)
  effectiveFrom        DateTime
  status               String   @default("ACTIVE")
  remark               String?
  createdBy            String
  createdAt            DateTime @default(now())
}
```

约束：

- 所有比例合计必须等于 `100%`。
- 修改比例只影响新生成的收益分配。
- 历史分配记录保存比例快照，不追溯。

### 5.6 收益分配明细表：`ProfitShareRecord`

```prisma
enum ProfitReceiverType {
  CUSTOMER
  DEPARTMENT
  CONTRACTED_USER
  CREATED_USER
  COMPANY
}

enum ProfitShareStatus {
  PENDING
  SETTLED
  CANCELLED
}

model ProfitShareRecord {
  id             String             @id @default(cuid())
  profitRecordId String
  receiverType   ProfitReceiverType
  receiverId     String?
  receiverNo     String?
  ratio          Decimal            @db.Decimal(5, 2)
  amount         Decimal            @db.Decimal(12, 2)
  status         ProfitShareStatus  @default(PENDING)
  settledAt      DateTime?
  createdAt      DateTime           @default(now())
}
```

说明：

- 客户收益、部门收益、签约员工收益、录入员工收益、公司收益都写入该表。
- 客户小程序只读取 `receiverType = CUSTOMER` 的分配结果，或直接读取聚合后的客户收益字段。

## 六、收益计算流程

### 6.1 后台录入产品收益

```text
后台录入产品周期收益
  ↓
保存为 ProductYieldPeriod(DRAFT)
  ↓
后台确认收益
  ↓
状态变为 CONFIRMED
  ↓
触发客户收益生成
```

### 6.2 生成客户收益

以产品总收益为基础，根据客户投资金额占比计算：

```text
产品本期总收益 = totalProfit
产品有效总投资 = sum(CustomerInvestment.amount)
客户投资占比 = customerInvestment.amount / 产品有效总投资
客户收益 = 产品本期总收益 × 客户投资占比
```

生成规则：

- 只计算 `ACTIVE` 状态的客户投资。
- 周期结束前已退出的投资是否参与，需要后续确认；一期建议不支持周期中退出。
- 生成前检查 `CustomerProfitRecord(investmentId, yieldPeriodId)` 是否已存在，防止重复生成。

### 6.3 生成收益分配明细

读取当前生效的 `ProfitShareConfig`。

```text
客户收益总额 = CustomerProfitRecord.profitAmount

客户分配 = 客户收益总额 × customerRatio
部门分配 = 客户收益总额 × departmentRatio
签约员工分配 = 客户收益总额 × contractedUserRatio
录入员工分配 = 客户收益总额 × createdUserRatio
公司分配 = 剩余金额或 customerProfit × companyRatio
```

为避免四舍五入误差：

- 前几项按比例向下保留 2 位小数。
- 最后一项用总额减去前几项，保证合计等于客户收益总额。

## 七、状态机

### 7.1 产品状态

```text
DRAFT → ACTIVE → CLOSED → ARCHIVED
```

说明：

- `DRAFT`：草稿，不允许客户投资。
- `ACTIVE`：可投资，可生成收益。
- `CLOSED`：停止新投资，但可继续查看历史收益。
- `ARCHIVED`：归档，只读。

### 7.2 产品周期收益状态

```text
DRAFT → CONFIRMED
   ↓
CANCELLED
```

说明：

- `DRAFT` 可编辑。
- `CONFIRMED` 后生成客户收益，不建议直接修改。
- 错误数据通过取消或冲正处理。

### 7.3 客户收益状态

```text
PENDING → CONFIRMED → SETTLED
   ↓
CANCELLED
```

说明：

- `PENDING`：系统生成，待后台复核。
- `CONFIRMED`：后台确认，可给客户展示。
- `SETTLED`：已结算。
- `CANCELLED`：冲正或取消。

## 十二、审计与风险控制

必须记录审计日志：

- 新建/修改产品。
- 产品启用/关闭。
- 新增客户投资。
- 录入产品周期收益。
- 确认产品周期收益。
- 生成客户收益。
- 修改收益比例配置。
- 收益结算。

主要风险：

| 风险 | 影响 | 处理建议 |
|------|------|----------|
| 产品收益录错 | 客户收益错误 | `CONFIRMED` 后不直接覆盖，通过取消或冲正处理 |
| 重复生成收益 | 收益重复入账 | 使用唯一约束 `investmentId + yieldPeriodId` |
| 比例变更影响历史 | 历史账务不可追溯 | 分配明细保存比例和金额快照 |
| 客户看到内部收益 | 信息泄露 | 客户门户接口只返回客户自己的收益 |
| 周期中投资变动 | 计算复杂 | 一期不支持周期中退出，后续再按持有天数加权 |

## 十三、实施阶段建议

### 阶段一：产品和投资基础

目标：

- 后台能维护产品。
- 后台能给正式会员创建投资记录。
- 客户小程序能查看自己的投资。

范围：

- `InvestmentProduct`
- `CustomerInvestment`
- 后台产品管理页面。
- 后台客户投资页面。
- 客户门户“我的投资”。

### 阶段二：产品周期收益

目标：

- 后台能录入产品周期收益。
- 系统能按投资占比生成客户收益。
- 客户小程序能查看收益明细。

范围：

- `ProductYieldPeriod`
- `CustomerProfitRecord`
- 后台收益维护页面。
- 客户门户“收益明细”。

### 阶段三：收益分配

目标：

- 后台能配置收益分配比例。
- 系统能生成客户、部门、签约员工、录入员工和公司分配明细。

范围：

- `ProfitShareConfig`
- `ProfitShareRecord`
- 后台收益分配页面。

### 阶段四：结算和报表

目标：

- 支持收益确认、结算、导出和审计。

范围：

- 结算状态流转。
- 收益报表。
- 导出 Excel。
- 冲正记录。

## 十四、待确认问题

1. 产品收益是按“产品总收益”录入，还是按“产品收益率”录入？
2. 客户收益是否需要按持有天数加权？一期建议不做。
3. 投资是否允许中途追加或部分退出？一期建议不做，只支持新增投资和整体退出。
4. 收益分配比例是全局统一，还是按产品配置？一期建议全局统一。
5. 客户小程序展示的是“客户应得总收益”，还是只展示“客户分配后实际到账收益”？建议展示客户分配后实际到账收益，同时后台保留完整计算链路。
6. 收益结算是否需要对接实际付款流水？一期建议只做手动结算状态。

---

## 十五、推荐落地顺序

建议先做阶段一和阶段二：

1. 产品管理。
2. 客户投资。
3. 产品周期收益。
4. 客户收益记录。
5. 小程序客户收益展示。

收益分配比例、内部人员/部门收益和结算报表可以作为阶段三、阶段四推进。

这样既能让客户先看到投资收益，又不会把内部财务分配复杂度一次性压到第一版。
