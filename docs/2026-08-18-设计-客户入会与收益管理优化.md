# 客户入会与收益管理优化设计

> 日期：2026-08-18  
> 状态：设计稿  
> 适用范围：客户入会、正式会员账号、签约归属、收益分配与后续后台管理

---

## 一、背景与目标

当前系统已经支持客户录入、会员申请、审批和分成记录，但新的业务要求对“客户”“会员”“收益”三类概念提出了更清晰的边界：

1. 客户没有缴费前不是正式会员，只能是意向会员。
2. 客户成为正式会员后，需要生成唯一客户编号，并允许客户使用“客户编号 + 密码”登录小程序查看自己的信息。
3. 客户来源、录入人、分享人、签约人可能不是同一个人，需要分别记录。
4. 后续收益管理不只依赖会员费分成，还要支持按客户投资收益配置多方收益比例。

本设计目标是把现有“会员审批通过即有效”的模型调整为“缴费确认后正式入会”，并为后续收益管理预留稳定的数据基础。

---

## 二、核心结论

推荐采用 **方案 A：客户主档 + 入会记录 + 收益分配记录**。

客户表保存客户当前主档、来源归属、签约归属和正式会员账号信息；入会记录保存某次入会缴费与审批快照；收益记录保存每次投资收益及分配快照。

这个方案符合：

- **KISS**：不引入复杂账户体系，先复用客户主档和现有小程序登录能力。
- **YAGNI**：暂不做复杂投资产品、合同、支付网关，只记录业务必需字段。
- **SOLID**：客户身份、入会流程、收益分配各自独立，后续扩展不会互相污染。
- **DRY**：员工编号、部门编号、权限规则复用现有组织模型，不再另建一套人员体系。

---

## 三、方案对比

### 方案 A：客户主档承载当前归属，业务记录保存历史快照（推荐）

客户表新增签约人、签约部门、正式会员编号、客户登录密码等字段；会员入会和收益分配记录保存当时的签约人、录入人、分享人、部门快照。

优点：

- 查询客户详情直观，客户当前状态一眼可见。
- 历史收益可追溯，不受员工离职、调部门影响。
- 改动集中，适合在现有系统上演进。

缺点：

- 客户表字段会增加，需要控制字段含义，避免变成“万能表”。

适用场景：

- 当前阶段业务仍以客户管理和人工确认流程为主。
- 需要快速支持客户登录和收益分配。

### 方案 B：新增独立会员账户表 `CustomerAccount`

客户主档只保存客户信息，正式会员登录账号、密码、状态全部放入独立账户表。

优点：

- 身份体系更干净，后续支持多登录方式更方便。
- 客户与账号可以解耦。

缺点：

- 当前需求下复杂度偏高。
- 需要增加更多关联、接口和权限判断。

适用场景：

- 后续明确会支持一个客户多个账号、家庭账户、企业多联系人登录。

### 方案 C：继续复用现有 `Membership.memberNo` 作为客户登录编号

不新增客户编号，直接让会员号承担登录编号。

优点：

- 改动最小。

缺点：

- 客户可能续费、多次入会，会员号和客户身份会混淆。
- 不利于长期客户资产管理。

结论：

- 当前推荐 **方案 A**。
- 暂不采用 B，避免过早复杂化。
- 不建议 C，因为它会把“客户身份”和“入会记录”绑定死，后续收益管理会变乱。

## 四、业务概念重新定义

### 4.1 客户状态

建议将客户状态从简单的 `ACTIVE / INACTIVE` 扩展为更贴近业务的状态。

```prisma
enum CustomerStatus {
  PROSPECT      // 意向客户/意向会员，未缴费
  ACTIVE_MEMBER // 正式会员，已缴费并生成客户编号
  INACTIVE      // 停用/无效
}
```

规则：

- 新录入客户默认 `PROSPECT`。
- 只有完成缴费确认后，才能变为 `ACTIVE_MEMBER`。
- `ACTIVE_MEMBER` 必须有唯一 `customerNo`。
- 客户未缴费时不能用客户编号登录小程序。

### 4.2 入会记录状态

现有 `MembershipStatus` 建议调整语义，不再把审批通过等同于正式会员。

```prisma
enum MembershipStatus {
  PENDING        // 待提交或待审批
  APPROVED       // 审批通过，待缴费
  PAYMENT_PENDING // 待确认缴费
  PAID           // 已缴费，正式生效
  REJECTED       // 已拒绝
  EXPIRED        // 已到期
  REFUND_PENDING // 退款待审批
  REFUNDED       // 已退款
}
```

一期也可以少加一个状态：

- 保留 `APPROVED` 表示审批通过待缴费。
- 新增 `PAID` 表示已缴费正式生效。

推荐先采用“最小改动版”，只新增 `PAID`，减少迁移成本。

## 五、客户主档字段设计

### 5.1 当前已有归属

当前客户已经有：

| 字段 | 含义 |
|------|------|
| `assignedTo` | 当前维护人 |
| `createdBy` | 录入人 |
| `referredBy` | 分享人 |
| `referrerEmployeeNo` | 分享人员工编号快照 |
| `referrerDepartmentId` | 分享人部门 |
| `departmentId` | 当前客户所属部门 |
| `registrationSource` | 自助/人员/后台录入来源 |

这些字段继续保留。

### 5.2 新增签约归属

客户表建议新增：

```prisma
contractedBy          String?   // 签约员工 user.id
contractedEmployeeNo  String?   // 签约员工编号快照
contractedDepartmentId String?  // 签约部门 ID
contractedAt          DateTime? // 签约时间
```

说明：

- `contractedBy` 用于关联当前员工记录。
- `contractedEmployeeNo` 是关键追溯字段，即使员工离职也保留。
- `contractedDepartmentId` 记录签约归属部门，用于后续收益分配。
- 如果员工离职，员工记录不删除，只改为 `INACTIVE`，编号仍唯一保留。

是否把签约字段放在客户表？

- 放客户表：用于展示客户当前签约归属，查询方便。
- 同时在入会记录、收益记录里保存快照：用于历史追溯。

这不是重复设计，而是“当前状态 + 历史快照”的组合。

### 5.3 正式会员登录字段

客户表建议新增：

```prisma
customerNo       String?   @unique // 正式会员客户编号
passwordHash     String?           // 客户小程序登录密码哈希
memberActivatedAt DateTime?        // 正式会员激活时间
lastLoginAt      DateTime?
```

编号规则建议：

```text
C + 年月 + 6 位流水
示例：C202608000001
```

规则：

- 只有客户状态变为 `ACTIVE_MEMBER` 时生成。
- 编号生成后不可修改、不可复用。
- 客户注销或失效后编号仍保留。
- 密码必须哈希存储，不保存明文。

## 六、入会流程优化

### 6.1 推荐流程

```text
营销中心人员录入/分享客户
        ↓
客户成为意向会员 PROSPECT
        ↓
选择签约人和签约部门，提交入会申请
        ↓
负责人/后台审批
        ↓
审批通过：APPROVED，等待缴费
        ↓
后台确认缴费
        ↓
Membership → PAID
Customer → ACTIVE_MEMBER
生成 customerNo 和客户登录初始密码
        ↓
客户可用客户编号 + 密码登录小程序
```

### 6.2 为什么缴费确认才正式入会

业务上“审批通过”只代表内部同意客户入会，不代表客户已经履行付款义务。正式会员必须以缴费确认为准。

这能避免：

- 审批通过但客户未付款，系统却展示为正式会员。
- 未付款客户提前登录会员小程序。
- 收益、分成、报表提前入账。

## 七、入会记录快照设计

`Membership` 建议补充签约和来源快照：

```prisma
contractedBy            String?
contractedEmployeeNo    String?
contractedDepartmentId  String?

createdBySnapshot       String?
createdEmployeeNo       String?
createdDepartmentId     String?

referredBySnapshot      String?
referredEmployeeNo      String?
referredDepartmentId    String?

paidAt                  DateTime?
paidAmount              Decimal? @db.Decimal(12, 2)
paymentConfirmedBy      String?
```

说明：

- `contractedBy` 是本次入会签约人。
- `createdBySnapshot` 是客户最初录入人。
- `referredBySnapshot` 是客户分享人。
- 快照字段用于保证历史不变。
- 如果客户后续维护人、签约人变更，不影响已经生成的入会记录。

一期可以先落地最关键字段：

- `contractedBy`
- `contractedEmployeeNo`
- `contractedDepartmentId`
- `paidAt`
- `paymentConfirmedBy`

## 八、客户小程序登录设计

### 8.1 登录入口

新增客户登录接口：

```http
POST /api/auth/customer-login
```

请求：

```json
{
  "customerNo": "C202608000001",
  "password": "******"
}
```

登录校验：

- `customerNo` 存在。
- `Customer.status = ACTIVE_MEMBER`。
- `passwordHash` 校验通过。
- 客户未停用。

返回 token 中建议区分身份类型：

```json
{
  "subjectType": "CUSTOMER",
  "sub": "customerId",
  "customerNo": "C202608000001"
}
```

### 8.2 客户可查看范围

一期建议客户只能查看：

- 我的基础信息。
- 我的会员状态。
- 我的缴费记录。
- 后续：我的收益记录。

客户不能查看：

- 员工信息。
- 其他客户。
- 部门数据。
- 分成和后台收益配置。

## 九、收益管理设计

### 9.1 收益概念

这里的收益不是现有会员费分成，而是客户投资后产生的收益分配。

示例：

```text
客户投资：100 万
实际收益：10 万
配置比例：
客户 60%
部门 20%
签约员工 10%
录入员工 10%
```

生成结果：

```text
客户获得：6 万
部门获得：2 万
签约员工获得：1 万
录入员工获得：1 万
```

### 9.2 新增收益配置表

```prisma
model ProfitShareConfig {
  id                    String   @id @default(cuid())
  customerRatio          Decimal  @db.Decimal(5, 2)
  departmentRatio        Decimal  @db.Decimal(5, 2)
  contractedUserRatio    Decimal  @db.Decimal(5, 2)
  createdUserRatio       Decimal  @db.Decimal(5, 2)
  companyRatio           Decimal  @default(0) @db.Decimal(5, 2)
  effectiveFrom          DateTime
  status                 String   @default("ACTIVE")
  remark                 String?
  createdBy              String
  createdAt              DateTime @default(now())
}
```

约束：

- 所有比例合计必须等于 `100%`。
- 配置修改只影响新收益记录。
- 历史收益记录保存比例快照，不追溯修改。

### 9.3 新增收益记录表

```prisma
model CustomerProfit {
  id                   String   @id @default(cuid())
  customerId            String
  investmentAmount      Decimal  @db.Decimal(12, 2)
  profitAmount          Decimal  @db.Decimal(12, 2)
  occurredAt            DateTime
  status                String   @default("PENDING")

  contractedBy          String?
  contractedEmployeeNo  String?
  contractedDepartmentId String?
  createdBy             String?
  createdEmployeeNo     String?
  createdDepartmentId   String?

  configId              String?
  createdByOperatorId   String
  createdAt             DateTime @default(now())
}
```

### 9.4 新增收益分配明细表

```prisma
model CustomerProfitShare {
  id              String   @id @default(cuid())
  profitId        String
  receiverType    String   // CUSTOMER / DEPARTMENT / CONTRACTED_USER / CREATED_USER / COMPANY
  receiverId      String?
  receiverNo      String?
  ratio           Decimal  @db.Decimal(5, 2)
  amount          Decimal  @db.Decimal(12, 2)
  status          String   @default("PENDING")
  settledAt       DateTime?
  createdAt       DateTime @default(now())
}
```

说明：

- `CustomerProfit` 是一次收益事件。
- `CustomerProfitShare` 是收益拆分明细。
- 后续结算、对账、导出都以明细表为准。

## 十、收益计算规则

计算输入：

- 客户 ID
- 投资金额
- 收益金额
- 生效收益配置
- 客户当前或入会快照中的签约人、录入人、部门

计算步骤：

```text
1. 读取当前生效 ProfitShareConfig
2. 校验比例合计 = 100%
3. 读取客户签约人、录入人、签约部门
4. 创建 CustomerProfit
5. 按比例生成 CustomerProfitShare 明细
6. 明细状态初始为 PENDING
7. 财务确认后变为 SETTLED
```

边界规则：

- 签约人和录入人是同一人：可以生成两条不同角色明细，也可以合并展示；底层建议保留两条，便于解释比例来源。
- 签约人已离职：仍按员工编号快照生成收益明细。
- 录入人缺失：该比例归公司或待人工处理，建议一期进入“异常待处理”。
- 部门停用：历史收益仍记到原部门编号/ID。

## 十一、后台管理改造

### 11.1 客户详情

新增展示区：

- 客户身份：意向会员 / 正式会员。
- 客户编号：正式会员才显示。
- 录入人、分享人、签约人。
- 录入部门、分享部门、签约部门。
- 入会缴费状态。

新增操作：

- 设置/变更签约人。
- 提交入会申请。
- 确认缴费。
- 重置客户登录密码。

### 11.2 入会管理

列表增加筛选：

- 待审批。
- 审批通过待缴费。
- 已缴费正式会员。
- 已拒绝。

关键操作：

- 审批通过不再直接生成正式会员。
- 确认缴费后才生成客户编号、激活客户账号、生成收益/分成基础记录。

### 11.3 收益管理

新增菜单：

- 收益配置。
- 收益录入。
- 收益分配明细。
- 收益结算。

一期建议只做：

- 后台录入客户收益。
- 系统自动按比例拆分。
- 后台查看明细。
- 手动标记已结算。

## 十三、数据迁移建议

### 第一步：新增字段和枚举

- `Customer.status` 增加 `PROSPECT / ACTIVE_MEMBER`。
- 新增客户编号、客户密码、签约字段。
- `MembershipStatus` 新增 `PAID`。

### 第二步：迁移历史数据

建议规则：

- 现有 `Membership.status = APPROVED` 且 `paidAt` 不为空：客户设为 `ACTIVE_MEMBER`。
- 现有 `Membership.status = APPROVED` 且 `paidAt` 为空：保持待缴费，不生成正式客户编号。
- 无有效会员记录的客户：设为 `PROSPECT`。

如果历史数据里 `APPROVED` 已经代表已缴费，需要先确认业务口径，再批量设置 `paidAt` 和 `PAID`。

### 第三步：初始化客户编号

对正式会员按历史创建时间生成：

```text
C + 年月 + 6 位流水
```

编号生成后不可变更。

## 十四、权限与安全

### 员工端

- 只有营销中心、市场部、事业部可录入和维护客户。
- 发展中心、服务中心仍然只读。
- 确认缴费建议仅开放给后台管理员或财务角色。

### 客户端

- 客户登录 token 必须和员工登录 token 区分。
- 客户只能访问 `customer-portal` 下的接口。
- 客户密码必须哈希存储。
- 初始密码建议强制首次登录修改。

### 审计

以下操作必须写审计日志：

- 设置签约人。
- 入会审批。
- 缴费确认。
- 生成客户编号。
- 重置客户密码。
- 新增或修改收益比例。
- 录入收益。
- 结算收益。

## 十五、实施计划

### 阶段一：入会正式化

目标：

- 未缴费客户仍是意向会员。
- 缴费确认后才生成正式客户编号。

任务：

1. 调整 `CustomerStatus` 和 `MembershipStatus`。
2. 新增客户编号和客户密码字段。
3. 新增缴费确认接口。
4. 后台入会页面增加“审批通过待缴费”状态。
5. 小程序客户登录接口和基础信息页。

### 阶段二：签约归属

目标：

- 客户可以记录签约人和签约部门。
- 入会记录保存签约快照。

任务：

1. 客户表增加签约字段。
2. 入会记录增加签约快照。
3. 客户详情支持设置签约人。
4. 入会申请时允许选择签约人。

### 阶段三：收益管理

目标：

- 后台可配置收益比例。
- 客户收益可按比例自动拆分。

任务：

1. 新增收益配置表。
2. 新增客户收益表。
3. 新增收益分配明细表。
4. 后台收益录入和分配明细页。
5. 客户小程序展示个人收益。

## 十六、风险与处理

| 风险 | 影响 | 建议 |
|------|------|------|
| 历史 `APPROVED` 口径不清 | 可能误生成正式会员 | 迁移前先确认历史审批是否等同缴费 |
| 签约人、录入人、分享人混淆 | 收益分配争议 | 字段命名和页面展示必须明确角色 |
| 员工离职后收益追溯困难 | 历史账务不可信 | 所有业务记录保存员工编号快照 |
| 收益比例频繁变化 | 历史计算不可复盘 | 收益明细保存比例和金额快照 |
| 客户登录和员工登录混用 | 权限泄露 | token 增加 `subjectType` 并隔离接口 |

## 十七、待确认问题

1. 历史系统中 `APPROVED` 是否已经代表客户实际缴费？
2. 缴费确认由谁操作：系统管理员、财务人员，还是营销中心负责人？
3. 客户编号是否需要体现地区、市场部或年份？当前建议不体现组织，避免组织调整影响编号。
4. 签约人是否必须属于营销中心体系？建议一期强制是营销中心、市场部、事业部人员。
5. 收益比例是否全公司统一，还是允许按客户、产品或部门配置？建议一期全公司统一。
6. 录入人和签约人为同一人时，收益是否叠加给同一人？建议底层叠加，展示可合并。

---

## 十八、推荐落地顺序

推荐先做：

1. 客户状态与缴费确认。
2. 正式客户编号和客户登录。
3. 签约人、签约部门字段。
4. 入会记录快照。
5. 收益配置和收益明细。

不建议一开始就做：

- 第三方支付对接。
- 多产品投资账户。
- 多客户联系人账号。
- 自动财务凭证。

这些能力可以在正式会员和收益主链路稳定后再扩展。
